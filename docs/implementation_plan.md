# PlayPair 实施计划

## 1. 文档目的

本文档用于指导 PlayPair 项目的选题确认、项目提案、Alpha 版本开发以及后续课程交付。

当前项目仍处于方案阶段。文中内容按以下状态区分：

- **已知约束**：来自课程文件或当前小组情况。
- **建议方案**：根据课程评分重点、开发资源与技术风险提出，尚需小组确认。
- **待决策事项**：必须由小组或导师进一步确认。

## 2. 项目结论与定位

### 2.1 是否继续该选题

**建议继续，不更换课题。**

这个选题同时具备真实用户问题、完整软件工程链路、可展示的 AI 应用和可开展实验评估的核心机制，能够覆盖课程对需求、架构、实现、测试和技术深度的要求。

但项目不能停留在“普通聚会网站接入 AI”的层面。推荐定位为：

> 面向已有朋友圈，综合成员时间、硬性约束和软偏好，生成并解释群体聚会方案的可解释决策系统。

项目的核心研究与工程问题是：

> 如何在确保聚会方案满足确定性约束的同时，利用 Jev 对难以用固定规则表达的群体偏好进行快速、低成本且带置信度的判断，并生成忠实于真实决策依据的用户解释？

### 2.2 目标用户

长期产品愿景可以面向全体年轻人，但概念验证版本建议聚焦：

> 在同一城市生活、需要协调线下聚会的年轻朋友群体。

Alpha 阶段可以进一步限定到阿伯丁，以便使用规模可控、可验证的本地地点和活动数据。

### 2.3 核心价值

- 降低群聊中反复协调时间、地点和活动的成本。
- 避免只照顾表达最积极成员的偏好，提高群体决策公平性。
- 给出可执行的聚会方案，而非只有零散建议。
- 展示推荐依据、牺牲项和模型置信度，使结果可理解、可复核。
- 在模型不确定时转为人工投票，而非强行自动决定。

- 问题与目标用户是否有可信证据支持。

## 4. 产品范围

### 4.1 核心用户流程

1. 用户注册或登录通用账号。
2. 用户创建朋友圈或通过小组码加入朋友圈。
3. 成员填写近期空闲时段。
4. 成员填写硬性约束和活动偏好。
5. 系统计算可行的时间、地点与活动组合。
6. Jev 对候选方案进行结构化语义评价。
7. Go 服务综合确定性指标与 Jev 输出，产生排序结果。
8. 生成式大模型将真实决策记录转述为自然语言解释。
9. 用户查看前三个方案及其取舍；低置信度时由成员投票。

### 4.2 硬约束与软偏好

Alpha 必须区分两类输入：

#### 硬约束

硬约束由程序验证，候选方案不得违反。Alpha 建议至少包含：

- 所有成员或最低参与人数的可用时间。
- 人均最高预算。
- 明确排除项，例如无障碍要求、年龄限制、饮食禁忌或明确拒绝的活动。

#### 软偏好

软偏好允许折中，可由 Jev 评价，例如：

- 活动类别偏好。
- 室内或室外。
- 安静或热闹的氛围。
- 熟悉体验或新奇体验。
- 个体偏好与群体整体接受度。

时间、价格、距离和参与人数等精确计算不能交给 Jev。

### 4.3 非目标

Alpha 阶段不追求：

- 面向所有城市的完整地点数据库。
- 由 AI 自由浏览互联网并直接生成未知地点。
- 完整社交网络、聊天系统或好友动态。
- 复杂日历平台同步。
- 支付、预订或商业化功能。
- 自主执行任意工具调用的开放式 Agent 循环。

## 5. 核心技术方案

### 5.1 Jev 的正确角色

Jev 是 TypeSafe AI 推出的 System One 模型。它接收状态和类型化问题，并返回结构化结果。当前公开原语包括：

- `Choice`：从预定义候选中选择，并返回各选项概率和置信度。
- `Score`：依据预定义等级评价，并返回分数、概率分布和置信度。
- `Noul`：回答一个是非判断，并返回“是”的概率。

Jev 适合处理快速、有限、语义性的判断，不适合：

- 日期和时间比较。
- 数学及精确数值计算。
- 长链条推理。
- 生成解释文本。
- 自主选择工具和下一步动作。

因此，Jev 应当作为普通软件工作流中的决策原语，而不是整个系统的自主 Agent。

### 5.2 推荐架构

```text
成员时间、硬约束和软偏好
              │
              ▼
Go 服务：规范化输入并执行硬约束
              │
              ▼
产生少量可行的时间 + 活动 + 地点候选
              │
              ▼
Jev：并行评价语义匹配、群体接受度和冲突风险
              │
              ▼
Go 服务：组合确定性分数、概率与置信度
              │
              ▼
生成式 LLM：根据决策记录生成自然语言解释
              │
              ▼
展示前三名方案；低置信度时转为成员投票
```

建议的组件边界：

| 组件 | 责任 |
|---|---|
| Web 前端 | 账号、入组、偏好与时间填写、结果展示、投票 |
| Go API | 业务流程、鉴权、数据持久化、候选生成、模型编排 |
| Constraint Engine | 时间交集、预算、距离、排除项和最低参与人数检查 |
| Decision Provider | 封装 Jev 请求、返回概率和置信度，支持替换与模拟 |
| Ranking Engine | 合并确定性指标和 Jev 结果，输出可审计排名 |
| Explanation Provider | 将结构化决策记录转述为自然语言，不负责重新决策 |
| Data Store | 用户、小组、偏好、可用时间、地点、决策运行和反馈 |

### 5.3 Go 与 Python 的取舍

**Alpha 建议只使用 Go 后端，不增加 Python 微服务。**

理由：

- Jev 提供标准 HTTP API，Go 可以直接调用。
- 当前 Python 微服务不会带来不可替代的能力。
- 两名后端和 AI 开发者同时维护跨语言部署、接口和故障处理会增加风险。
- 课程更重视架构合理性、可靠性和可复现性，而不是服务数量。

Go 侧应定义可替换接口，例如：

- `DecisionProvider`：生产环境实现为 `JevProvider`，测试和离线演示实现为 `MockProvider`。
- `ExplanationProvider`：封装生成式模型，并允许使用模板作为降级方案。
- `VenueProvider`：Alpha 使用固定目录，后续可替换成地图或地点 API。

只有在后续确实需要 Python 专属算法、数据处理或实验库时，才考虑拆分独立服务。

### 5.4 决策流程

建议将一次决策运行设计为可审计的固定工作流：

1. 验证成员输入是否完整。
2. 将时间转换为统一时区和固定时间片。
3. 计算满足最低参与人数的可行时间窗口。
4. 从地点目录中排除违反预算、距离和禁忌的项目。
5. 枚举并裁剪候选组合，避免把大规模无关状态交给 Jev。
6. 将群体偏好拆成若干狭窄、相互独立的 Jev 问题。
7. 根据确定性分数、Jev 概率和显式权重计算最终排名。
8. 若整体置信度低于阈值，输出多个候选并请求人工投票。
9. 保存输入快照、候选集、模型版本、问题定义、响应、最终分数和解释依据。
10. 生成解释并返回前三个推荐方案。

### 5.5 可解释性的边界

生成式大模型生成的语言本身不构成可信解释。解释必须基于已保存的决策证据，例如：

- 哪些成员在该时段有空。
- 哪些硬约束被满足。
- 哪些共同偏好得到满足。
- 哪些偏好没有满足以及原因。
- 确定性分数、Jev 概率与置信度。
- 该方案相对其他候选的主要优势。

生成式模型只能转述这些事实，不得添加新地点、新约束或不存在的用户偏好。系统应验证解释中引用的事实能够追溯到决策记录。

## 6. 数据策略

### 6.1 Alpha 地点和活动数据

建议使用 20–40 个阿伯丁本地地点或活动组成的固定结构化目录。字段至少包括：

- 名称与类别。
- 地址或坐标。
- 价格区间。
- 典型开放时段。
- 室内或室外。
- 氛围和活动标签。
- 年龄、无障碍、饮食或其他限制。
- 数据来源与最后核验日期。

固定目录能够提高演示稳定性、测试可重复性和结果可验证性。

### 6.2 后续数据扩展

Beta 或后续版本可以接入地图或 Places API，获取真实候选，再由系统过滤和排序。不建议让联网大模型直接自由搜索并把生成内容当成事实，因为这会带来：

- 地点不存在或信息过期。
- 开放时间、价格和限制不准确。
- 同一输入无法复现实验结果。
- 外部网络或模型故障导致演示失败。

## 7. Alpha 版本

### 7.1 Alpha 定义

Alpha 是项目最小的端到端可演示版本。Alpha 完成后，即使后续功能未能实现，也不应影响最终核心演示。

“核心跑通”不能只定义为 Jev API 返回成功，而应证明整个决策链路能够产生可靠、可解释的结果。

### 7.2 Alpha 必须实现

- 创建小组或使用小组码加入。
- 为若干演示成员填写空闲时段。
- 填写至少预算、排除项和若干软偏好。
- 使用固定地点与活动目录。
- 由 Go 计算可行时间并执行硬约束。
- 产生至少 10 个可行候选。
- 调用 Jev 对候选或偏好维度进行结构化评价。
- 综合排名并返回前三个方案。
- 展示 Jev 的概率或置信度，以及推荐依据和牺牲项。
- 低置信度时提示用户投票或人工确认。
- Jev API 不可用时使用可复现的 Mock 或降级结果完成演示。

### 7.3 Alpha 验收标准

Alpha 应同时满足：

1. 不推荐违反硬约束的方案。
2. 相同种子数据能够重复运行和演示。
3. 每个推荐理由都能追溯到输入、规则或模型结果。
4. 无共同时间时返回明确、可处理的结果，而不是崩溃。
5. Jev 低置信度时不会伪装成确定答案。
6. Jev 超时、限流或返回错误时系统能够降级。
7. 从提交偏好到获得结果的完整流程可以在演示中顺利完成。

### 7.4 Alpha 建议不做

- 第三方日历同步。
- 实时地图搜索。
- 自动预订和支付。
- 完整聊天或通知系统。
- 复杂好友关系。
- 自然语言填写所有用户信息。
- 自主执行工具的开放式 Agent。

## 9. 用户研究与需求证据

### 9.1 是否值得进行访谈和问卷

**值得，并且应尽早进行。**

用户研究不仅用于证明“年轻人可能有需求”，还应直接影响需求、优先级、评价指标和最终结论。这样能够加强技术报告中问题、需求、设计和测试之间的一致性。

### 9.2 建议研究规模

- 6–10 个半结构化访谈。
- 30–50 份短问卷。
- 后期邀请 4–6 个真实朋友圈进行任务测试或可用性测试。

在开始收集数据前，应向导师确认是否需要课程研究伦理审批，并采用最小化数据原则。

### 9.3 建议研究问题

优先询问已经发生的行为，而不是仅询问用户是否喜欢设想中的产品：

- 最近一次组织聚会花费了多长时间？
- 哪一步最容易产生反复讨论或最终取消？
- 当前使用什么工具协调？哪些信息散落在不同工具中？
- 时间、预算、地点和活动偏好中，哪类冲突最常见？
- 是否发生过部分成员的偏好长期被忽略？
- 用户愿意让 AI 自动决定到什么程度？
- 用户需要看到什么证据才愿意接受推荐？
- 低置信度时更愿意重新推荐、投票还是由组织者决定？

应避免只问“你会不会使用这个产品”，因为这类主观意愿对真实需求的证明较弱。

## 10. 测试与评价方案

### 10.1 软件测试

- **单元测试**：时间区间、预算、距离、最低参与人数、候选过滤和排名公式。
- **组件测试**：Jev Provider、解释 Provider、地点 Provider 和数据库层。
- **接口测试**：前后端 API、错误码、超时、重试和幂等性。
- **端到端测试**：从加入小组到获得并确认推荐。
- **可靠性测试**：Jev 超时、限流、无共同时间、无可用地点和输入缺失。
- **性能测试**：候选数量增加时的响应时间和模型调用成本。

### 10.2 决策质量评价

建议至少比较以下方案：

1. 简单规则或加权排序基线。
2. Go 硬约束加 Jev 语义评价的推荐架构。
3. 如时间允许，加入普通生成式 LLM 直接选择候选的实验对照。

评价指标可包括：

- 硬约束违反率。
- 用户最终接受率或 Top-3 命中率。
- 群体满意度均值。
- 最不满意成员的评分，用于衡量公平性。
- 决策响应时间。
- 单次决策成本。
- 重复运行的一致性。
- Jev 置信度与实际接受结果的关系。
- 解释事实错误率或不可追溯陈述比例。
- 用户对解释清晰度和信任度的评分。

不能只把“Jev 返回了结构化 JSON”当成算法有效性的证据。

### 10.3 需求追踪

从 Alpha 开始维护需求追踪矩阵：

| 需求 ID | 用户问题 | 功能或质量需求 | 设计组件 | 测试或评价证据 |
|---|---|---|---|---|
| 示例：FR-TIME-01 | 群聊难以找到共同时间 | 系统应返回满足最低参与人数的时间窗口 | Constraint Engine | 时间区间单元测试与端到端场景 |

最终技术报告、PoC 和展示应引用相同的需求 ID、架构名词和测试结果。

## 11. 团队组织建议

当前已知团队共有 10 人，其中 2 人预计负责后端和 AI，其余 8 人承担前端、研究、测试和文档等工作。

不建议将 8 人笼统分配为“前端和文书”。课程要求使用小组工作量档案，贡献需要可衡量，因此应拆成独立且可验收的工作流。

建议责任域如下：

| 责任域 | 建议人数 | 主要成果 |
|---|---:|---|
| 后端与数据模型 | 1 | Go API、数据库、约束引擎、部署 |
| AI 与决策评估 | 1 | Jev 工作流、排名、解释、实验数据 |
| 前端核心流程 | 2–3 | 入组、填写信息、推荐结果和投票界面 |
| 用户研究与需求 | 1–2 | 访谈、问卷、需求规格和用例 |
| 测试与质量 | 1–2 | 测试计划、测试用例、结果和缺陷跟踪 |

以上是责任域，不代表成员只能在一个领域工作。每项任务都应有负责人、协作者、截止日期和可验证产物。代码、研究材料、测试记录、图表和报告章节都应进入统一的版本或任务管理流程。

## 15. 当前推荐决策摘要

- 保留当前课题，但将其聚焦为可解释的群体聚会决策系统。
- Alpha 同时决定时间、活动和地点，但只在有限、可信的候选中选择。
- 时间、预算、距离和排除项由 Go 执行；Jev 只负责语义性的软偏好评价。
- 生成式大模型只解释已产生的决策证据，不负责重新决定结果。
- Alpha 不引入 Python 微服务，Go 直接调用 Jev HTTP API。
- Alpha 使用经核验的阿伯丁固定地点目录，不依赖联网大模型自由搜索。
- 尽快进行小规模访谈和问卷，并用结果支持需求与最终评价。
- 以端到端可靠演示和可量化评价为核心，不以功能数量为目标。
